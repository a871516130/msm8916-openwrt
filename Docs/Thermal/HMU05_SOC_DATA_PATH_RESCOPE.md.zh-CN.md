变更内容：
- OpenWrt **确实**投票总线带宽。实况 interconnect_summary 显示 mas_apss / slv_ebi_ch0 cpu0 峰值 = 8,528,000 kBps 随 CPU 频率跟踪。互连驱动（CONFIG_INTERCONNECT_QCOM_MSM8916=y，补丁 834）活跃并以正确的主线 RPM ID 发送 RPM 投票（slv_ebi_ch0 slv_rpm_id=0，bimc_snoc 99/130，snoc_bimc 101/132，pcnoc_snoc 29/45）。
- RPM 固件是**共享硅片**（非 OS 相关）。Android（msm_bus）和 OpenWrt（interconnect）向同一 RPM 发送相同的 RPM 带宽投票，RPM 对任一 OS 以相同方式缩放 DDR/BIMC 时钟。因此总线投票**不能**解释 OpenWrt-vs-Android 温度差距。若要说，Android 投票更多带宽，会让总线更热。
- 之前"bimc_ddr_clk_src = 800 MHz 意味着总线不缩放"的读取是 Linux 视图伪影：该时钟由 RPM 管理且**无频率表**，因此 Linux 无法观察 RPM 驱动的频率变化。

动作：**不要**移植 Android msm_bus ID（错误命名空间，不必要）。总线投票杠杆对于 OS 差距问题已**关闭**。改为运行**受控的等吞吐量** A/B（见更正后审计文档）。

# HMU05：SoC 数据路径热工作 —— 重新定范围

**日期：** 2026-10-09
**硬件：** HMU05 4G LTE 棒（`hmu05,250605v0s`，Qualcomm MSM8916）
**分支：** `test/thermal`

---

## 为何重新定范围

更早的"负载差距是 SoC 数据路径 / 调制解调器 DSP 功率差异"框架严重依赖
**一个假设 —— A2 引脚保持** —— 此后被**驳斥**（见下文）。单独地，
一个干净的*测得*成因（CPU 轨，成因 #3）现已**修复**。因此数据路径
工作需要新的、基于证据的范围，而非旧范围。

---

## 现已确定的内容（不要重新争辩）

| 声明 | 裁定 | 证据 |
|---|---|---|
| **Android 收起 A2；OpenWrt 钉住它 → +10–12 °C** | **已驳斥 —— 对等** | `android_idle.csv`：`a2_out/a2_in/a2_pwr` **恒定，0 次转换** ⇒ Android 保持 A2 **开** = OpenWrt 的引脚。测得钉住−未钉住**空闲**差约 **+2.8 °C**。（[ROOT_CAUSE](./HMU05_OPENWRT_ANDROID_THERMAL_ROOT_CAUSE.md)） |
| **Wi-Fi 在 Android 上禁用** | **已驳斥 —— 对等** | Android `wlan0` UP + SoftAP 桥；两个固件都运行 Wi-Fi。 |
| **Android 的 thermal-engine 节流 PA/调制解调器** | **不受支持** | 无 `thermal-engine.conf`（编译进默认）；`fusion`（调制解调器 QMI）仅在 **105 °C** 触发 ⇒ 约 62 °C 时未激活。 |
| **降低跳闸点（75 → 60/65 °C）** | **作为修复已驳斥** | 受控测试：**0 °C 收益**，**rx −37 %**，永久空闲节流回归。 |
| **CPU 轨固定在约 1.15 V（成因 #3）** | **已修复** | Qualcomm **CPR** 移植（补丁 841–846）；轨现 **1.0625 V** == Android。（[CPU_RAIL_CPR_PORT](./HMU05_CPU_RAIL_CPR_PORT.md)） |
| **从 AP 进行 DDR/互连缩放** | **已关闭（惰性）** | `bimc_ddr_clk_src` 无 freq_tbl / 仅 RPM；Android 无此类时钟。 |

**后果：** 两个"大"负载差距假设（A2 引脚，PA/调制解调器节流）都已死，且
一个干净信号（轨）已修复。**我们目前不知道负载差距的多少
剩余。**

---

## 必须首先控制的混杂

每个先前 OpenWrt-vs-Android *负载*比较都携带不受控差异：
**LTE 吞吐量差约 2×**（Android ≈ 0.59 MB/s vs OpenWrt ≈ 1.15 MB/s）。更多字节/s = 更多
无线电/DSP/CPU 工作 = 更多热。**任何不均衡吞吐量的负载 A/B 都不可解释。**

过去运行中的其他不受控变量：**环境温度**、**LTE 频带/信号（RSRP/SINR）**、
以及**采样窗口 vs 热稳态**。

---

## 重新定范围计划

### 步骤 0 —— 重测残余差距（post-CPR）

**问题：** 现在轨是 1.0625 V（Android 对等），OpenWrt−Android 负载差距多大？

**协议（预先登记）：**
1. 相同物理 HMU05，刷 Android → 测量 → 刷 OpenWrt → 测量（或用两个保存转储）。
2. **均衡吞吐量** —— 在两者上将下载限速到固定速率（例如 0.5 MB/s），或
   在*相同*窗口下载*相同*固定大小负载。
3. **记录并匹配**：环境、LTE 频带 + RSRP/SINR、CPU 频率、所有 6 个 TSENS、PMIC、以及 CPU 轨。
4. 保持到**稳态**（60 s 内无 ≥0.5 °C 变化），然后比较均值。
5. 每固件 n ≥ 3 次运行。

**决策规则：** 若匹配吞吐量/环境下的稳态差距在 SoC 传感器上 **≤ 约 3 °C**，
差距有效关闭（轨是成因）→ **停止**。若差距剩余，转到步骤 1。

### 步骤 1 —— 隔离幸存者（仅当步骤 0 显示真实差距）

仅这些候选幸存；按此顺序测试（最便宜/最干净优先）：

| 候选 | 测试 | 为何可能重要 |
|---|---|---|
| **GPU 策略** | Adreno GPU 在无显示棒上是否甚至活动？检查两者负载下 `gpu` 时钟 + `gpu-thermal`。Android 的 thermal-engine 在 **55 °C** 限制 GPU。 | 仅当 GPU 运行时重要。可能**惰性**（无显示）。 |
| **WLAN 策略** | 比较两者 Wi-Fi TX 功率/速率和 `wlan` 热路径。Android 在 **60 °C** 限制 WLAN。 | 仅当 Wi-Fi 承载流量时重要。 |
| **无线电/TX 条件** | 在**匹配吞吐量**下比较 MCS / TX 功率 / 频带 / RSRP-SINR。 | 旧"差距"可能部分是 2× 吞吐量差异。 |
| **调制解调器 DSP 活动** | 在匹配吞吐量下比较调制解调器侧活动计数器（非 A2 域状态 —— 那是对等）。 | 若 DSP 在 OpenWrt 上每字节做更多工作，那是真实线索。 |

**不再是候选：** A2 引脚、Wi-Fi 开/关、PA/调制解调器 thermal-engine 缓解、跳闸点。

---

## 诚实的预期

真实可能性是**步骤 0 显示差距基本关闭** —— 因为：
- 一个干净受控信号（纯 CPU 负载 ⇒ 等频时 SoC +4 °C / PMIC +16 °C）被
  归因于**轨**，现已修复，且
- 剩余"负载差距"数字全部带 **2× 吞吐量混杂**和
  不受控环境拍摄。

若发生，正确结论是**"成因 #3 是修复；其余是测量
伪影"** —— 且热工作流关闭。我们应愿意得出该结论。
